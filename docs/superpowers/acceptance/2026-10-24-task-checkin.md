## 上線前待辦

C2 的資料表和函式在正式站還不存在，而合併後的網站與每晚備份都會讀它們，所以**一定要先在正式站套用 migration，再合併 PR**（和 C1 相同）。

1. **套用 migration**：在正式站 Supabase 的 SQL Editor 貼上並執行 `supabase/migrations/20261024150000_checkin_c2.sql`。只貼 `migrations/` 底下的檔案，不要貼 `supabase/tests/` 的（測試檔有 psql 專用的 `\set`）。
2. **確認 pg_cron 與排程**：

   ```sql
   select extname from pg_extension where extname = 'pg_cron';
   select jobname, schedule, active from cron.job;
   ```

   第一個要有一列；第二個要看得到 `noon-archive-due`、`*/5 * * * *`、`active = true`。如果沒有 pg_cron，先到 Dashboard 的 Database → Extensions 啟用，再重跑 migration 最後的排程那一段。
3. **確認資料表與預設任務**：`noon_items`、`noon_days`、`noon_day_items`、`noon_day_students`、`noon_marks` 都存在；每個既有班級已有 5 項 `noon_items`（`select class_id, count(*) from noon_items group by 1`）。
4. **AC39 驗證（正式站，用維護者測試帳號的班級，不碰老師的資料）**：
   1. 用測試帳號登入正式站，到「中午時段」，打一兩筆卡，確認有紀錄。
   2. 16:55 前關掉所有網站分頁，並讓操作的裝置離線或關機。
   3. 17:05 以後，在 SQL Editor 查：

      ```sql
      select jobid, status, start_time, return_message
      from cron.job_run_details order by start_time desc limit 5;

      select date, status, archived_by, scheduled_archive_at, archived_at
      from noon_days where class_id = '<測試班級 id>' order by date desc limit 3;
      ```

      期望：`archived_by = 'schedule'`，`archived_at` 在 17:00–17:05 之間，`cron.job_run_details` 有對應的成功紀錄。
   4. 再執行兩次 `select noon_archive_due();`（SQL Editor 以管理者身分），回傳 0，`noon_days` 仍只有一份。
   5. 把結果（時間、截圖）記回本表 AC39，改成 ✅。
5. **請老師在教室實測 AC44**：iPad 加入主畫面、進入教室模式，用電子白板請學生實際點一輪，一般任務和中午時段各做一次：每位學生都點得中自己的名字，快速連點不會變成取消。結果記回本表。
6. **AC31–AC33**：在設定頁下載備份，由開發者在本機 Supabase 還原並比對各表筆數（含 `noon_*`、`checkin_events`），也試一個壞檔，結果記回本表。
7. **AC23 補充**：請老師用 Excel 開一次四種匯出檔，確認中文不亂碼、筆數與畫面一致。
8. **AC35、AC37**：用瀏覽器離線模式試打卡，確認 SaveStatus 顯示失敗與重試；iPad 打卡後，用老師的手機確認看得到。
